# Exa project rules (`exa/`)

These apply on top of the root `CLAUDE.md`. Its agent model policy and team workflow still hold. That policy is about the Claude Code agents that write the code; the product's own runtime models are listed in `web/src/lib/agent/models.ts` and include fast models on purpose.

## Ownership

- This folder is Asadullah's. Nafay owns Dock: `/web`, `/infra` and `/.github/workflows/` at the repo root. Do not edit those. If a change needs them, say so instead.
- Everything for this project stays inside `exa/`. Edit shared root files (`CLAUDE.md`, `README.md`, `.env.example`, `.gitignore`, `research/`, `.claude/`) only with small changes, and name them in the commit message.

## Git

- Asadullah pulls and pushes by hand. Claude commits only, on a branch named `asad/<topic>`, and never pushes.
- Before starting work, see what Nafay's side has landed since the last pull: `git log origin/main -10` and `git branch -r`. Nafay's agents merge into `main` often.

## The app (`exa/web`)

- Read `README.md` (one level up) for what is built and the code map, and `web/AGENTS.md`: this is Next.js 16 and AI SDK 7, and both differ from older versions. Their docs ship in `node_modules/next/dist/docs/` and `node_modules/ai/docs/`. Check names there, not from memory.
- Exa's API changed a lot in 2026. Before changing an Exa call, read `reports/Exa Internet Butler playbook.md`. Call Exa through `web/src/lib/exa/client.ts` so cost tracking and caching keep working.
- A tool returns the payload its widget renders; the shapes live in `web/src/lib/widgets/types.ts`. Every payload carries `sources`, and every widget shows them.
- Tools that stream progress are async generators. The last value they `yield` is the result; a generator's `return` value is ignored by the AI SDK.
- Reasoning is never replayed across turns (see the comment in `web/src/app/api/chat/route.ts`). Keep it that way: it is what makes model switching and context trimming safe.
- Sift (`web/src/lib/agent/tools/sift.ts`) checks many pages against the user's wishes with Gemini's decision model, through `web/src/lib/decisions/client.ts`. The judge is only ever given what Exa returned, and "the page does not say" stays a third answer beside yes and no: do not fold it into no. One request carries every page and every question (at most 1,000 questions); the field names are the ones in `node_modules/@google/genai` (`decisions.create`) and the docs (aistudio.google.com/docs/decisions-api). After touching either file run `pnpm smoke decisions` and one real question through the app.
- The landing page (`web/src/components/landing/`) is for the web only and for people who are not signed in: `/` shows it to them, the app to everyone else, and the desktop app never (`src/proxy.ts`, `src/app/page.tsx`). Most of what it shows is the app itself: the real widgets with their fixtures, loaded as they come near the screen (`live.tsx`), so a change to a widget shows there too. Nothing on it may reach the server: `live.tsx` keeps requests to `/api/*` on the page while the landing page is on screen, and a card whose controls would act for an account is `inert`. What cannot be live (the desktop app at work, a call, the Jobs page) is a real screenshot in a frame of its own proportions; retake those rather than drawing the interface, and never let a frame crop one. Each feature says what powers it (see the rule on naming models). The desktop downloads are listed in `web/src/lib/downloads.ts`, built by `pnpm desktop:release` (`desktop/pack.mjs`) and served by `/download/[id]`; packaging must never write into a folder a running copy of the app was started from.
- Wording that a user reads (the landing page, the welcome screen, buttons, dialogs, errors) is written the way a good product site writes: a short headline, one plain line, concrete numbers over adjectives, contractions where natural. No em dashes, no "seamless", "powerful", "unlock" or "effortless", no lists of three adjectives, nothing that explains what is already on screen. Read it aloud before keeping it.
- Stock quotes come from Exa's market pages, which read differently while the US market is closed (evenings, weekends, holidays): "closed at $162.85, down $3.34 (2.01%) on Fri, Nov 13", with no minute-by-minute table, and plus signs on an up day. `parseStockPage` in `web/src/lib/agent/tools/markets.ts` reads both forms; a closed market is an answer (`closed: true`, the last close), not an error, and the card and the agent both say the market is closed. If a quote fails, look at what the page says before anything else.
- New widgets follow `web/WIDGETS.md` and get a fixture so they show up in `/dev/widgets`.
- Before committing: `pnpm typecheck`, `pnpm lint`, and for anything that touches the agent, one real question through the running app.
- A task belongs to the server (`web/src/lib/runs.ts`), not to the request that started it: `/api/chat` never passes the request's abort signal to the model, only the run's own, which Stop (`DELETE /api/chat/[id]/run`) and the usage limit use. The server saves the conversation itself and, while a task is running or has just ended, its copy wins over what the interface sends (`serverCopy`). The interface joins a running task by putting the conversation back as the task found it and asking for the stream from its start through its ordinary send path (`REJOIN` in `butler.tsx`); do not switch that to the AI SDK's `resume`, which rebuilds only the last request's parts and loses the earlier ones of an answer written across several requests. A conversation left while working stays mounted and hidden; anything in `ChatView` that should only happen on screen checks `hidden`. After touching any of this run `pnpm test:background <port>`.
- The user picks a mode and an effort, never a model. Nothing the interface shows, and nothing the server sends it, may name a model or a thinking setting: the interface imports `lib/agent/modes.ts` and `lib/agent/stats.ts`, never `lib/agent/models.ts` (the only place that ties a mode to a model). Requests carry `mode` and `effort`; routes turn them into a model with `pickMode(body.mode, user.modes)` and `modelForMode`, so an account can never run a mode the admin has not given it. Messages a user reads say "mode", and a missing key is logged, not shown. The admin's pages are the exception: they show models. So is the landing page, which says what powers each feature ("Powered by Gemini 4 Carbon, Gemini 4 Hydrogen, Claude Opus 5.5, Claude Sonnet 5.5", "Gemini 3.8 Live" for voice, "the Gemini Decisions API" for Sift, Exa for search) because the user asked for that there; when a model behind a mode changes in `models.ts`, change those lines too.
- What an answer used is grouped as LLMs, Exa, Voice and Decisions (`lib/agent/stats.ts`, `spendOf`). An account with `showUsage` off is not sent the figures at all (`/api/chat` strips them); keep any new figure behind the same check. The usage limit (`lib/db/cap.ts`) is checked at the start of every route that spends money and between the steps of a running task; a new route that runs a model or calls Exa must start with `capFor(user)` too.
- Thinking and effort settings live in `web/src/lib/agent/options.ts`, one entry per model and job, with the effort dial (1 to 4) mapped for the agent job. Claude and Gemini take different parameters, and models inside a family reject different values. After changing that file or adding a model, run `pnpm smoke options` (30 small requests against the live APIs).
- Web and desktop are one codebase and one server. The desktop app (`web/desktop/`) loads the interface from the server and adds the live browser. Do not fork the interface for either: use `clientKind()` / `useDesktopApp()` where they differ. The web gets no browser tools (`createTools`) and its instructions say to point people to the desktop app; keep both in step when adding a tool that acts.
- The live browser's engine (`web/src/lib/browser/`: `session.ts`, `guard.ts`, `snapshot.ts`, `engine.ts`) runs in the desktop app's main process, bundled by `desktop/build.mjs`. It must not import `server-only`, Next or anything from the server; the server must not import `session.ts` or `engine.ts`. The agent's browser tools have no `execute` on the server: the interface hands each step to the app (`butler.tsx`, `lib/browser/client.ts`).
- A browser task that is waiting on the user (an approval, a page handed to them) must survive a reload and a closed app. The page cannot, so nothing may pretend it did: `settle()` in `web/src/lib/conversations.ts` leaves the waiting step open (desktop app, its own conversation, less than a day old), `ChatView` asks the app for it again with `again: true`, and the engine answers a step it does not know with `missed` instead of taking it on whatever page is there. A hand-over whose page is gone is answered `interrupted`. The engine is reset when the interface is loaded afresh (`did-navigate` in `desktop/main.cjs`, not earlier: the old page would report its waiting step as declined). Leaving a conversation stops only that conversation's own steps. After touching any of this run `pnpm test:waiting <port>`.
- A chat's address is `/chat/<id>` and the app keeps it in step itself (`showInAddress` in `web/src/components/butler/butler.tsx`, with `history.pushState` / `replaceState`, which Next's router follows). Do not turn those moves into router navigations: `/` and `/chat/[id]` are two pages that render the same shell, and a navigation between them would take the shell down, along with the chats working out of sight. Opening a chat is asynchronous and the latest move wins (`moves`): keep that check on anything new that changes which chat is shown. `web/src/proxy.ts` lists the private pages (`PRIVATE_PAGES`); a new page that needs an account goes on that list and still checks the session itself.
- Words: a "chat" is a conversation (the button says "New chat"); a "job" is something scheduled. Do not write "task" in anything a user reads, and tell the agent the same in its instructions.
- Jobs (`web/src/lib/jobs/`, `web/src/lib/db/jobs.ts`, `web/src/lib/agent/tools/jobs.ts`): a job only looks things up and writes. A run gets the web's tools minus the ones that wait for a person and the ones that manage jobs (`NOT_IN_A_RUN` in `run.ts`); never give a run a browser tool or a way to ask the user. Schedules from the model are checked in code (`checkSchedule`: a real cron line, at least 5 minutes apart, a time that has not passed), and times without an offset are the user's own clock (`momentOf`). The Jobs page cannot change a schedule (its `PATCH` ignores one); only the agent's `updateJob` can. Every run records its usage with kind `job` and starts with `capFor`; keep both. The clock runs inside the one server process (`scheduler.ts`); a job is taken by moving it on to its next run, so a second process would not run it twice, but do not rely on that to scale out. After touching any of this run `pnpm test:jobs <port>`.
- Notifications (`web/src/lib/notifications/`): whether an email is sent is decided in one place, `notify()`: the account's settings, whether a window of theirs is in front (`lib/presence.ts`), and for "waiting for you" a minute's wait. Do not send email from anywhere else, and do not email a notice kind without a setting for it. A job's result is the one email that goes out while the user is here. What the agent wrote goes into an email only through `markdownToEmailHtml`, which drops raw HTML: text from the web must not be able to put markup into someone's inbox. Emails are checked against Resend's test inbox (`delivered+…@resend.dev`), never a real address.
- Every agent step goes through `guard.ts`. Payment, passwords and one-time codes are refused in code; anything that commits the user waits for approval inside the engine. Do not loosen a rule to make a site work: hand the page to the user instead. After touching `guard.ts` run `pnpm test:guard`; after touching anything in `lib/browser/`, `desktop/` or `components/browser/` run `pnpm test:desktop <port>` with the server up (it uses a throwaway profile and signs in with the admin from `.env.local`). Never test a real booking, order or message on a real site past the approval step; use `/dev/sandbox.html`.
- The app shows a site at desktop width, drawn smaller when the view is narrow. That layout width can be lost when a page arrives, so the engine checks it before every step that measures the page (`keepFit` in `session.ts`): a button measured in one layout and ringed over another points at empty space. Keep that check in any new step that reports where something is.
- Do not open a remote-debugging port in the app, do not open a browser outside the app, and do not add anything that hides the agent from sites (no automation-hiding switches, no stealth plugins): the view is honest about being Beryl. The agent's mouse goes through `sendInputEvent` and its keys only after the view holds the keyboard (`desktop/relay.cjs`); keep both, or its input lands in the interface instead of the page.
- Accounts and data (`web/src/lib/db/`, `web/src/lib/auth/`): every API route that touches someone's data starts with `requireUser()` (or `requireAdmin()`), and every query is scoped to that user. `/api/chat` and `/api/conversations` are outside the proxy on purpose (large bodies) and check for themselves. After changing `schema.ts` run `pnpm db:generate` and commit the migration; after changing auth or the conversations API run `pnpm test:auth <port>`. There is one admin, from `ADMIN_EMAIL`/`ADMIN_PASSWORD`; never add a way to make another. Never print or commit the admin password.
- A conversation is continued only in the kind of client it was started in (`origin`). The server enforces it in `/api/chat` and the conversations API; the interface shows the note.
- Voice (`web/src/lib/voice/`, `web/src/components/voice/`, `web/src/app/api/voice/`): the browser talks to Gemini's Live API directly with a short-lived token from `/api/voice/token`; the API key must never reach the browser, and everything the agent is told or may do goes into the token's locked config, not into what the interface sends. A call writes into the conversation's own messages (`live-call.ts`), so a tool part it writes must have the same shape a typed conversation would produce. A step that commits the user is approved by a press on screen, never by voice. Check Gemini's names in the docs (aistudio.google.com/docs/live-api) and in `node_modules/@google/genai`, not from memory: they change. After touching voice run `pnpm test:voice <port>`.
- The name and the logo's shapes are in `web/src/lib/brand.ts`. After changing the logo run `pnpm icons`, and update the two hand-copied files it names.
- Production is described in `DEPLOYMENT.md` (Google Cloud project `beryl-exa`). The server runs as exactly one always-on Cloud Run instance because running tasks live in its memory: do not raise its instance count, and remember that every deploy or settings change restarts it and drops the tasks in progress. Production secrets live in Secret Manager, never in the repo or the image. Do not sign in to the live site with the admin's password from a script or a browser you drive: check it through `/api/health` and ask the user to sign in.
- Keys go in `exa/.env.local`. Add every new variable name to `exa/.env.example` with an empty value.
